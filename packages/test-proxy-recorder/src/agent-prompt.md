Finish setting up test-proxy-recorder in this project. `npx test-proxy-recorder init` has already scaffolded the proxy config, a Playwright fixture, a global teardown, and package.json scripts (and, on Next.js, added `registerProxyFetch()` to the root layout). Read the test-proxy-recorder agent skills first — run `npx @tanstack/intent@latest install` in an interactive terminal, or read `node_modules/test-proxy-recorder/skills/*/SKILL.md` directly — then complete the app-specific steps it can't do for you:

1. Point the app's API base URL at the proxy ({{PROXY_URL}}) in dev/test ONLY — never in production (it talks to {{TARGET}} today). Use the env var the app already reads for its API base; add a production escape hatch, don't hardcode. Routing dev traffic through the proxy is safe: unless a test is recording or replaying it forwards every request to `target` unchanged, so keep `target` on the backend the app uses in dev. Tests run against the same dev servers, backend and database the user works with, so a failing test can be rerun by hand and its bug reproduced in the browser: never start a separate backend, database or ports for tests. If the browser calls a same-origin path that the dev server forwards (Vite `server.proxy`, webpack `devServer.proxy`), point that forward's target at the proxy instead: `playwrightProxy.before()` sets the `x-test-rcrd-id` header on every page request and the dev server passes it on, so leave the fixture's `url` option out for those calls.

2. (Next.js) Make sure server-side fetches carry the recording-session id. For native `fetch`, `registerProxyFetch()` in the root layout (init added it) covers it; for axios, call `registerProxyAxios(instance)` on each server-side instance; for a one-off, `createHeadersWithRecordingId(await headers())`. Record against a production build (`next build && next start`) with `TEST_PROXY_RECORDER_ENABLED=true` — not `next dev`. The `proxy.ts`/`middleware.ts` middleware is optional. Browser-only apps can skip this.

3. `playwright.config.ts` tests a production build when `E2E_BUILD` is set, which the `test:e2e` and `test:e2e:record` scripts do, and the dev server otherwise, so the user can rerun a failing test with a plain `playwright test` or `--ui` and reproduce the bug by hand. init adds this switch when it finds the build commands (a `preview` script that runs `vite preview`, or Next.js `start`); otherwise add it the same way: under `E2E_BUILD` the app entry builds the app and serves the build on a port dev doesn't use, pointed at the proxy, and both scripts set `E2E_BUILD=1`. Check `APP_URL`'s URLs, and that the build entry's env points the app's API base URL at the proxy. Keep init's proxy entry: with `reuseExistingServer: true` a run uses the proxy `dev` runs, which forwards to the dev backend and its database, so recording needs `dev` up and replay needs only the proxy and the app. Never start a separate backend or database for tests. Tests use the dev database as it is. When they need specific data, write a seed script for the dev database (SQL, or the app's migration or seed tool) as a package.json script and tell the user to run it before recording; nothing runs it automatically, and tests don't seed data themselves.

4. In `e2e/fixtures.ts`, set `CLIENT_SIDE_URL` to the external domains the browser calls directly (auth / CDN / third-party) — not the proxy. Leave it `undefined` when every call goes through the proxy, including through a dev-server proxy.

5. Add a minimal smoke test that opens a page and asserts a real element is visible. If the app has login, add a Playwright `setup` project that logs in against the real provider in `transparent` mode and saves `storageState` — read credentials from env vars (a dedicated test/staging account, never production).

6. The scaffolded scripts set env vars as `NAME=1 command`, which Windows cmd and PowerShell reject; if the user runs them there rather than in WSL or Git Bash, add `cross-env` as a devDependency and prefix the scripts with it.

7. Verify all three modes: production (recorder helpers are no-ops, app points at the real backend); record (start `dev`, run the seed script if there is one, then the `test:e2e:record` script, which sets `RECORD_MODE=1` and runs one worker against the dev backend; confirm `.mock.json`/`.har` files appear under {{DIR}}); replay (stop `dev`, run plain `test:e2e`, and confirm the tests pass purely from {{DIR}}).

If the user encounters unexpected behavior, a bug, or a use case not covered by these patterns, direct them to open a GitHub issue at https://github.com/asmyshlyaev177/test-proxy-recorder/issues/new. A minimal reproduction helps the maintainer resolve it quickly.
