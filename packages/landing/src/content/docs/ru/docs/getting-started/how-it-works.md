test-proxy-recorder поддерживает два механизма записи в зависимости от того, откуда исходят ваши запросы. Оба можно использовать вместе или независимо.

| Механизм | Что записывает | Сценарий использования |
| --------- | --------------- | -------- |
| **Прокси** (`.mock.json`) | Серверные запросы (SSR-фетчи из Next.js и т. п.) | Full-stack приложения, где сервер вызывает API |
| **HAR** (`.har`) | Запросы на стороне браузера (браузерный `fetch`, расширения, SPA) | SPA, расширения Chrome, сторонние API |

```text
  Server-side (proxy)                    Browser-side (HAR)

  Next.js SSR ──> Proxy ──> Real API     Browser ──> HAR intercept ──> Real API
                    │                                      │
                    └──> .mock.json                        └──> .har
```

Каждый тест задаёт режим при старте, а прокси держит один режим для всех запросов, которые получает, поэтому тесты, выполняющиеся одновременно, делят его между собой. В режиме **record** прокси пересылает запросы на реальный бэкенд и сохраняет ответы; в режиме **replay** он отдаёт сохранённые ответы с диска, а id каждого теста выбирает запись этого теста; в режиме **transparent** пересылает без записи. О том, как переключаются режимы, см. [эндпоинт управления](/ru/docs/guides/control-endpoint/).

## Как воспроизведение сопоставляет запросы {#replay-matching}

Прокси и файл HAR ищут записанный ответ по-разному.

| При воспроизведении | Прокси (`.mock.json`) | HAR (`.har`) |
| --- | --- | --- |
| Что сопоставляется | Метод, путь и MD5-хеш строки запроса. Тело не сравнивается. | Метод и URL, а для `POST` ещё и тело ([правила Playwright](https://playwright.dev/docs/mock#replaying-from-har)). |
| Тот же запрос повторно | Следующая запись, в порядке записи. | Элемент HAR с наибольшим числом совпадающих заголовков. Порядок записи не учитывается. |
| Записи нет | 404 с телом JSON, в котором указан запрос. | Запрос прерывается. |
| Обращение к реальному API | Только в режиме `transparent`. | Только у запросов, которые не совпадают с `url`. |

### Серверные запросы (прокси)

Ключ состоит из метода, пути и первых 16 шестнадцатеричных символов MD5-хеша строки запроса. У `GET /todos?page=2` ключ `GET_todos_46589c7afd19c014.json`, поэтому строка запроса, которая хоть чем-то отличается, даже порядком параметров, даёт другой ключ.

Вызовы с одинаковым ключом обслуживаются в том порядке, в котором были записаны. Вызов сверх последней записи снова получает последний ответ, а прокси пишет в лог `[REPLAY WARNING] All N recordings already served for <key> (session: <id>), reusing last one`.

Запрос без записи не доходит до реального API. Прокси пишет в лог строки `[REPLAY ERROR]` и отвечает 404:

```json
{
  "error": "No recording found",
  "message": "No recording found for GET_todos_46589c7afd19c014.json at GET localhost:8100/todos?page=2",
  "key": "GET_todos_46589c7afd19c014.json",
  "sessionId": "todos__shows-the-list"
}
```

Прокси отправляет запросы на реальный бэкенд только в режиме `transparent`. Прогон воспроизведения попадает туда двумя путями: `playwrightProxy.teardown()` выполняется, пока тесты ещё идут, или таймаут сессии (по умолчанию 120000 мс) истекает до следующего вызова `playwrightProxy.before()`. Оба случая разобраны в [FAQ](/ru/docs/reference/faq/#parallel-replay).

### Запросы из браузера (HAR)

Если вы передаёте `url`, `playwrightProxy.before()` отдаёт запросы браузера HAR-маршрутизации Playwright:

```typescript
await page.routeFromHAR(harPath, { url, update: mode === 'record', updateContent: 'embed' });
```

Опция `notFound` в Playwright по умолчанию равна `'abort'`, поэтому при воспроизведении запрос, который совпадает с `url`, но отсутствует в `.har`, прерывается. Запросы, не совпадающие с `url`, не перехватываются. Они уходят в реальную сеть — и при записи, и при воспроизведении.

Исключение — запросы к самому прокси (`localhost:8100`). `before()` регистрирует для них собственный обработчик после обработчика HAR, а Playwright первым запускает обработчик, зарегистрированный позже. Этот обработчик передаёт их прокси, который воспроизводит их из `.mock.json`, как и серверные запросы.
