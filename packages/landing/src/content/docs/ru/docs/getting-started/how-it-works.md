test-proxy-recorder поддерживает два механизма записи в зависимости от того, откуда исходят ваши запросы. Оба можно использовать вместе или независимо.

| Механизм | Что записывает | Сценарий использования |
| --------- | --------------- | -------- |
| **Прокси** (`.mock.json`) | Серверные запросы (SSR-фетчи из Next.js и т. п.) | Full-stack приложения, где сервер вызывает API |
| **HAR** (`.har`) | Запросы на стороне браузера (браузерный `fetch`, расширения, SPA) | SPA, расширения Chrome, сторонние API |

```text
  Server-side (proxy)                    Browser-side (HAR)

  Next.js SSR ──> Proxy ──> Real API     Browser ──> HAR intercept ──> Real API
                    │                                      │
                    └──> .mock.json                        └──> .har
```

Каждый тест задаёт режим при старте, а прокси держит один режим для всех запросов, которые получает, поэтому тесты, выполняющиеся одновременно, делят его между собой. В режиме **record** прокси пересылает запросы на реальный бэкенд и сохраняет ответы; в режиме **replay** он отдаёт сохранённые ответы с диска, а id каждого теста выбирает запись этого теста; в режиме **transparent** пересылает без записи. Прокси запускается в режиме transparent, поэтому приложение, запущенное через него вне тестов, обращается к своему бэкенду как обычно. О том, как переключаются режимы, см. [эндпоинт управления](/ru/docs/guides/control-endpoint/).

## Как воспроизведение сопоставляет запросы {#replay-matching}

Прокси и файл HAR ищут записанный ответ по-разному.

| При воспроизведении | Прокси (`.mock.json`) | HAR (`.har`) |
| --- | --- | --- |
| Что сопоставляется | Метод, путь и MD5-хеш строки запроса. Тело не сравнивается. | Метод, URL и тело, затем элементы с наибольшим числом общих заголовков запроса, так как одинаковые URL и тело могут означать разные операции, которые различаются по заголовку. Если такого тела нет ни в одном элементе, сопоставление идёт по методу и URL, а граница multipart (boundary) не учитывается. |
| Тот же запрос повторно | Следующая запись, в порядке записи. | Следующая запись, в порядке записи, с одним правилом для изменяющих запросов (см. ниже). |
| Записи нет | 404 с телом JSON, в котором указан запрос, а `playwrightProxy.before()` закрывает страницу, так что тест сразу падает (`failOnMissingRecording: false` это отключает). | Запрос прерывается, и в лог пишется `[Client-Side Replay] No recorded response for <method> <url>`. |
| Обращение к реальному API | Только в режиме `transparent`. | Только у запросов, которые не совпадают с `url`. |

### Серверные запросы (прокси)

Ключ состоит из метода, пути и первых 16 шестнадцатеричных символов MD5-хеша строки запроса. У `GET /todos?page=2` ключ `GET_todos_46589c7afd19c014.json`, поэтому строка запроса, которая хоть чем-то отличается, даже порядком параметров, даёт другой ключ.

Вызовы с одинаковым ключом обслуживаются в том порядке, в котором были записаны. Вызов сверх последней записи снова получает последний ответ, а прокси пишет в лог `[REPLAY WARNING] All N recordings already served for <key> (session: <id>), reusing last one`.

Запрос без записи не доходит до реального API. Прокси пишет в лог строки `[REPLAY ERROR]` и отвечает 404:

```json
{
  "error": "No recording found",
  "message": "No recording found for GET_todos_46589c7afd19c014.json at GET localhost:8100/todos?page=2",
  "key": "GET_todos_46589c7afd19c014.json",
  "sessionId": "todos__shows-the-list"
}
```

Прокси отправляет запросы на реальный бэкенд только в режиме `transparent`. Прогон воспроизведения попадает туда двумя путями: `playwrightProxy.teardown()` выполняется, пока тесты ещё идут, или таймаут сессии (по умолчанию 120000 мс) истекает до следующего вызова `playwrightProxy.before()`. Оба случая разобраны в [FAQ](/ru/docs/reference/faq/#parallel-replay).

### Запросы из браузера (HAR)

Если вы передаёте `url`, `playwrightProxy.before()` записывает подходящие запросы браузера средствами записи HAR в Playwright:

```typescript
await page.routeFromHAR(harPath, { url, update: true, updateContent: 'embed' });
```

Воспроизведение выполняет собственный обработчик библиотеки на `page.route()`, который читает этот файл, а не `page.routeFromHAR()`. Воспроизведение Playwright на каждый повтор запроса отдаёт первый подходящий элемент HAR ([microsoft/playwright#18288](https://github.com/microsoft/playwright/issues/18288)), поэтому `GET` после `POST` показывал список в состоянии до `POST`. Обработчик библиотеки вместо этого отдаёт каждую запись один раз, в порядке записи, и повторно использует запись, только когда страница запрашивает чаще, чем при записи. Порядок читающих запросов относительно изменяющих задаёт одно правило. После того как воспроизведён изменяющий запрос к пути (любой метод, кроме `GET`, `HEAD` и `OPTIONS`, так что сюда попадает и GraphQL-запрос типа query), читающий запрос к этому пути или к вложенному в него пути предпочитает копии, записанные после изменяющего запроса. Если для читающего запроса не осталось копий до следующего такого изменяющего запроса, повторно используется последняя копия перед этим изменяющим запросом. Это правило сохраняет воспроизведение верным, когда приложение читает данные другое число раз, чем при записи, — например, при двойном запросе в строгом режиме React (strict mode). Записанный редирект отрабатывается внутри `.har`, потому что последующий запрос браузера никогда не доходит до `page.route()`: fetch получает конечный ответ, а навигация отправляется дальше, на цель редиректа.

Запрос, который совпадает с `url`, но отсутствует в `.har`, прерывается. Запросы, не совпадающие с `url`, не перехватываются, а в режиме `transparent` не перехватывается ни один запрос. Они уходят в реальную сеть.

Исключение — запросы к самому прокси (`localhost:8100`). `before()` регистрирует для них собственный обработчик после обработчика HAR, а Playwright первым запускает обработчик, зарегистрированный позже. Этот обработчик передаёт их прокси, который воспроизводит их из `.mock.json`, как и серверные запросы.
